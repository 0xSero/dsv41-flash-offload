# D130 -> D141 (2026-10-03): current default is D141, 1x RTX 3090 24 GB + EPYC 7443P + 503 GB DDR4

Changes vs D119/D123 (all in `docker/entrypoint.sh` defaults and `ct/ct_vllm.py`):
- prefix caching on; V4.1's ratio-2 compressor ring is empty at block-aligned hits, so a fresh ring is exact
  (measured: greedy tokens identical, |dlogprob| <= 0.03 at 4k/32k, 1e-5 at 131k)
- steps <= 512 tokens run the CPU-tier + zero-copy split path instead of streaming all 204 GB of cold experts
- elastic VRAM expert cache back (~395 slots): released only before > 512-token steps, rewarmed after 4 decode steps
- 8 DMA staging slots (deeper next-layer prefetch), chunk 8192
- scheduler: decode share 0.25 during long prefills; long-prompt chunks capped at 7168 only while >= 2 requests compete

All numbers: live server, OpenAI API, natural EOS, no max_tokens; unique cache_salt per request (cold prefill).

## D132 / D135 (later the same night)
- D132: CPU tier cost model DSV41_CT_B 0.24 -> 0.20 (the GPU zero-copy share was the long pole): C1/C2/C4 19.8 / 23.0 / 25.6.
- D135: the stock DMA prefill loop issued its first copies only when a MoE layer started, so the copy engine idled
  through every attention block (torch profile: 3.3 s of kernel-only time per 8k step). `runtime/patch_dma_prefetch.py`
  queues the next MoE layer's first batches after each layer. Steady prefill 8k / 64k / 261k: 787 / 769 / 694 tok/s
  (D130 ~710 / 700 / 620); greedy outputs identical; 30-min soak 58 requests (D132: 50), 0 errors, 0 OOM, VRAM peak
  23.1 GB. The first long prefill after a restart is ~25 % slower (pointer tables, kernel JIT).
- Rejected: 16k chunks + row-sliced linears (VRAM peak 24.07 of 24.58 GB), 12k chunks (23.9 GB, gains inconsistent),
  16 staging slots (no gain before the prefetch fix, smaller expert cache).

## D139 (morning)
- Hybrid for lone 513..1536-token steps (typical agent turns with prefix caching): the CPU tier computes the trailing
  DMA batches of each layer (count balanced from measured CPU cost per row) while the GPU streams the rest.
  TTFT 768 / 1024 / 1536 tokens: 6.7 / 6.7 / 7.7 s (D135 8.35 / 8.33 / 8.5). Above 1536 the host input copy and
  conversion eat the gain (4096: 9.7 s vs 8.8). Only active when one request is in the system.
- C1/C2/C4 18.7 / 23.1 / 24.5; prefix cache exact; 30-min soak 58 requests, 0 errors, 0 OOM.
- Soak medians swing several seconds between identical configs; compare configs on the throughput rows and repeated
  C1/C2/C4 runs, not on a single soak.

## D140
- Hybrid input path: the step input is copied to pinned host memory by the copy engine (the split kernel's single-block
  copy is skipped, `ct/ft_tier_cu_v.cu` policy entry 8) and the CPU tier converts it to fp32 on the whole thread pool
  (`kernels/cpu_avx2/ft_tier_ext.cpp`). TTFT 768 / 1024 / 1536 / 2048 tokens: 6.7 / 6.5 / 7.5 / 7.8 s (DMA-only 8.3-8.6);
  no gain above ~2k, so DSV41_CT_HYB_MAX=2048.
- C1/C2/C4 18.7 / 22.6 / 24.3; 64-token greedy continuations at 4k / 8k identical to D135; 30-min soak 56 requests,
  0 errors, 0 OOM, 0 CPU-tier timeouts.

## D141: full 256k window with agents
- Failure seen from Pi near 256k: compaction/summary calls send `max_tokens` (~13k) with a ~250k-token conversation;
  vLLM rejected prompt + max_tokens > 262144 with HTTP 400 at tokenization. `DSV41_CLAMP_MAX_TOKENS=1` validates the
  prompt against the whole window and lets vLLM's get_max_tokens give the request the room that is left.
- Verified: 250k + max_tokens 13107 was 400, now accepted; a full 249,042-token chat with max_tokens 13107 streamed to a
  natural stop (958 tokens, decode 19.2 tok/s at 250k context), 0 errors.
- D140 long soak (3 workers, stopped after ~75 min when the user became active): 83 requests, 0 errors, VRAM peak
